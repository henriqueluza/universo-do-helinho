## Decisões (tomadas sem humano)

- **Configuração, não código.** O formatador `json` é nativo de `Microsoft.Extensions.Logging.Console` e o host já lê `Logging:Console`; nenhum método de extensão foi necessário.
- **`json` é o padrão e `Development` é a exceção.** Assim qualquer ambiente novo (Staging, Production) já nasce em JSON. Alternativa descartada: `appsettings.Production.json`, que deixaria os outros ambientes em texto.
- **`TimestampFormat: "yyyy-MM-dd'T'HH:mm:ss.fff'Z'"`** (ex.: `2026-11-18T12:00:00.123Z`, o mesmo formato do exemplo de `observability.md`). Sem `TimestampFormat` o formatador JSON não escreve timestamp. Alternativa descartada: `"O"`, porque o `+` de `+00:00` sai escapado como `+` na linha bruta (o codificador do formatador não é configurável por `appsettings`). O `Z` é literal, então só é verdadeiro com `UseUtcTimestamp: true`; o teste de Production afirma as duas coisas.
- **`TimestampFormat: null` em Development.** As opções de `FormatterOptions` são compartilhadas entre os formatadores; sem anular, o formato legível ganharia um timestamp na frente de cada linha. Depende do .NET 10 preservar `null` do JSON de configuração; o teste de Development falha se isso deixar de valer (verificado removendo a linha: o valor herdado volta a aparecer).
- **`IncludeScopes: false`.** Os escopos do ASP.NET Core carregam `RequestPath`, `RequestId` e nome da página; o caminho pode levar identificador de registro, e qualquer `BeginScope` futuro entraria no log sem revisão. Custo: as linhas não têm `RequestId`/`TraceId` para correlação. Alternativa descartada: ligar os escopos agora; fica para a Issue de tracing (fora de escopo da #98).
- **SQL do EF em `Warning` em todos os ambientes**, inclusive Development (antes saía em `Information` no console local). Quem precisar ver SQL localmente sobe o nível por variável de ambiente (`Logging__LogLevel__Microsoft.EntityFrameworkCore.Database.Command=Information`).
- **Teste de vazamento em dois níveis:** com os níveis efetivos de Production e com tudo em `Trace` só para o provedor de captura (pior caso, se alguém aumentar a verbosidade para diagnosticar). O provedor também guarda os escopos, mesmo com `IncludeScopes` desligado no console.
- **Saída JSON validada sem tocar em `Console.Out`:** o teste resolve o `ConsoleFormatter` configurado no host e escreve em um `StringWriter`, o que evita estado global entre testes paralelos.

## Varredura de PII nas chamadas de log de `src/`

Só existem duas mensagens próprias (`FakeEmailSender`: "E-mail fake descartado."; `FakePushSender`: "Push fake descartado."), ambas sem parâmetro. Nenhuma interpola e-mail, usuário, matrícula, CPF, RG, token ou senha. Não há `UseHttpLogging`, `AddHttpLogging`, `EnableSensitiveDataLogging`, `BeginScope` nem escrita direta em `Console`.

Observações, sem ação:

- Em falha de conexão o EF Core registra em `Error` o nome do banco e o host do servidor (não a senha nem a connection string).
- O formatador JSON escapa caracteres fora do ASCII básico (`ã` vira `ã`, `+` vira `+`) na linha bruta. É JSON válido e qualquer leitor de JSON decodifica; trocar o codificador exigiria código (`JsonWriterOptions.Encoder`), o que a Issue pede para evitar.

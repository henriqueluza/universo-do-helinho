## Decisões (tomadas sem humano)

- **Divisão em duas fatias, diferente da sugerida.** A sugestão era "renderizador + dois modelos" e depois "os outros dois"; medido, isso daria ~520 linhas na primeira fatia, porque o peso está no renderizador e nos testes, não nos modelos. A divisão adotada separa por tipo de revisão: esta fatia é a parte sensível de segurança (encode, injeção de cabeçalho, link); a #207 é conteúdo, layout e design.
- **A #207 nasce de uma branch empilhada nesta** (`issue-207-email-modelos` a partir de `issue-205-email-modelos`), porque depende deste código e este PR não pode ser mergeado antes do ADR. É exceção à regra "sem branches empilhadas", registrada nos dois PRs.
- **`HtmlEncoder.Default`, o mais restrito:** letras acentuadas saem como entidade numérica (`ã` vira `&#xE3;`). É HTML válido em qualquer cliente e resiste a troca de charset no caminho. Alternativa descartada: liberar Latin-1 no codificador para o código-fonte do e-mail ficar legível.
- **Chaves viram parênteses no valor.** O corpo vai para a Brevo, que tem linguagem de modelo própria (`{{params.x}}`, `{{contact.EMAIL}}`); um nome de aluno com chaves não pode ser interpretado lá. Alternativa descartada: entidade numérica só no HTML, que deixaria o texto puro e o assunto sem proteção.
- **Caminho por lista de permissão**, em vez de lista de proibição: recusa `//`, `@`, `\`, `..`, `?`, `#`, espaço e quebra de linha de uma vez.
- **Exceções do framework** (`InvalidOperationException`, `ArgumentException`) em vez de um tipo próprio: ninguém precisa capturá-las de forma seletiva.
- **Subagentes `qa-tester` e `docs-writer` não foram disparados:** a verificação foi feita nesta sessão (comandos e resultados no PR) e não há documento de API, modelo de dados ou runbook a atualizar nesta fatia.

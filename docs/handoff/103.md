## Decisões tomadas sem humano
- **Sem `FrameworkReference` em `Infrastructure`.** O pacote traz `Microsoft.AspNetCore.DataProtection` como pacote NuGet, o que basta para `AddDataProtection` e `SetApplicationName`. Os testes de arquitetura não restringem `Infrastructure` e seguem verdes; nenhuma alternativa foi necessária.
- **Nome da aplicação `universo-do-helinho`**, em constante pública. Trocar o nome invalida todo cookie e token já emitido.
- **Filtro de log em código.** O repositório do pacote escreve o XML da chave (com o material secreto) em log no nível `Debug` ("Reading data with key ..., value ..."). Com o `appsettings.json` atual (`Microsoft.AspNetCore: Warning`) isso já não aparece; o filtro garante o mesmo se alguém aumentar a verbosidade do ASP.NET Core. Limite conhecido: uma regra de log específica de provedor (por exemplo `Logging:Console:LogLevel:...=Debug` para essa categoria) ainda venceria o filtro. Alternativa descartada: confiar só na configuração.
- **`PersistenceTests.Migracao_unica_...`** passou a esperar duas migrações (antes `Assert.Single`). É a exceção ao schema congelado autorizada pela Issue.
- **Tabela e colunas em PascalCase**, o padrão do pacote e a convenção que o `AppDbContext` já usa (`AspNetUsers`, `Badges`).
- **`dotnet-ef`:** não há manifest local de ferramentas; foi usada a `dotnet-ef` 10.0.3 global que já estava instalada na máquina (nada foi instalado). Ela avisa que é mais antiga que o runtime 10.0.14; a migração gerada foi conferida à mão.

## Testes (`tests/Helinho.IntegrationTests/DataProtectionKeysTests.cs`)
1. Valor protegido por uma instância é lido por outra instância nova no mesmo banco; a tabela tem chave. Controle negativo: apagadas as linhas, uma terceira instância não lê o valor.
2. Cookie `helinho.panel` do login do `master` do seed (senha sintética) é aceito por outra instância nova. Controle negativo: sem as chaves do banco, o cookie é recusado.
3. Com o Data Protection em `Trace`, nenhuma linha de log contém o material da chave.

Os controles negativos existem porque, numa máquina com diretório pessoal, o Data Protection sem persistência grava as chaves em `~/.aspnet/DataProtection-Keys` e os testes 1 e 2 passariam mesmo sem a tabela. Verificado por mutação: sem `PersistKeysToDbContext` os três testes falham; sem o filtro de log o teste 3 falha.

## Correção de 22/11/2026: `HospedagemTests` e o `validate` preso

**Sintoma.** Depois de receber a branch padrão, o `validate` do PR ficou com 2 falhas em `HospedagemTests` (`Proto_encaminhado_e_tratado_como_https_com_HSTS_e_cookie_Secure` e `Em_Development_nao_ha_redirecionamento_nem_HSTS_nem_cookie_Secure`) e o passo `dotnet test` não terminou (run 44451528642, de 19/11, cancelada pelo teto de 6 h; run 45084788128, de 22/11, presa).

**Causa das 2 falhas (confirmada).** Os dois testes pedem `/entrar` num host cujo banco nunca foi criado. Antes deste PR o token antiforgery era protegido com chaves locais; agora as chaves vêm da tabela `DataProtectionKeys`. Sem o esquema, a leitura do anel de chaves falha (`3D000: database ... does not exist`), o `Protect` lança `CryptographicException` e a página responde 500. Reproduzido no macOS e em contêiner Linux com o runtime do CI (10.0.15); é a mesma pilha do log do CI. Na branch padrão, sem este PR, os dois testes passam (o `validate` dos outros PRs está verde).

**Correção.** Só em teste, sem tocar em código de produção: os dois testes aplicam o `migrate` (o pre-deploy command do ADR-0002 §7.3) antes de pedir a página, que é a ordem que o deploy garante. Nenhuma asserção mudou. Teste novo em `DataProtectionKeysTests`: sem o esquema a proteção falha (não existe chave fora do banco) e o mesmo host volta a proteger depois do `migrate`, sem reiniciar.

**O `validate` preso: causa não confirmada.** O que foi medido:
- A subida do host carrega o anel de chaves de forma síncrona (`DataProtectionHostedService`). Com banco que aceita o TCP e não responde, a subida espera o `Timeout` da connection string. Os dois testes de banco mudo de `HealthTests` usam `Timeout=60` e, com este PR, levam cerca de 1 min cada, quase tudo na subida do host (medido no macOS e no Linux). Isso soma uns 2 min à suíte, mas termina.
- A suíte de integração inteira rodou até o fim em contêiner Linux (arm64, 4 CPUs, runtime 10.0.15, árvore de antes da correção): 18 min, sem travar. As falhas além das 2 de `HospedagemTests` foram de rede do próprio contêiner de diagnóstico (`Network is unreachable`).
- O travamento do runner (x64) não foi reproduzido. No log de 19/11 a última saída são as 2 falhas de `HospedagemTests`; depois, silêncio até o cancelamento.

Se o `validate` do commit da correção travar de novo, o próximo passo é diagnóstico no próprio runner (por exemplo `--hangdump` do Microsoft Testing Platform, que exige editar o workflow e, portanto, autorização humana).

**Efeito em produção a registrar.** Com o banco fora do ar na subida, a aplicação demora o `Timeout` da connection string (padrão do Npgsql: 15 s) para começar a atender e segue de pé; `/health/ready` responde 503 até o banco voltar.

## Riscos e próximo passo
- **Chaves em texto no banco** (aceito no ADR-0002 §9 para homologação). Cifrar em repouso (`ProtectKeysWith*`) fica para o ADR de produção. O pacote registra o aviso "No XML encryptor configured" ao criar uma chave; é esperado.
- **A migração precisa rodar antes de a aplicação atender.** Sem a tabela, o anel de chaves não carrega e páginas com antiforgery (inclusive `/entrar`) respondem 500; depois do `migrate` o mesmo host se recupera sozinho (coberto por `Sem_o_esquema_a_protecao_falha_e_volta_a_funcionar_depois_do_migrate_sem_reiniciar`). Hoje a migração roda pelo comando `seed`; o passo de deploy da Railway precisa garantir a ordem.
- **No primeiro deploy com este PR**, quem estava logado cai uma vez (anel de chaves novo e nome de aplicação novo). Depois disso o cookie sobrevive aos redeploys.
- **Próximo passo:** decisão D4 no PR #101; depois, revisão e merge por humano.

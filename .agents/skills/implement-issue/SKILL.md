# Implementar Issue

1. Leia a Issue com `gh issue view <numero>`. Confirme critérios de aceite claros e testáveis. Se não tiver, comente na Issue o que falta, aplique `needs-human` e pare — não assuma.
2. **Dependências:** para cada linha `Depende de #N` no corpo, confirme que #N está fechada (`gh issue view N --json state`). Se alguma estiver aberta, comente, aplique `blocked` e pare.
3. Atualize e crie a branch a partir de `main`: `git fetch origin && git checkout -b issue-<numero>-<slug-curto> origin/main`.
   **Marque o início** (evita que outro disparo pegue a mesma Issue e move o card para "Em andamento" no quadro): `gh issue edit <numero> --remove-label status:ready --add-label status:in-progress`. Se a label `status:in-progress` não existir no repositório, crie-a com `gh label create status:in-progress --color FBCA04 --force`.
4. **Padrões de engenharia:** carregue a skill `engineering-standards`; leia o guia da stack, o nível de arquitetura do ADR e `references/small-prs.md`. Se a Issue é de CI, build, infra ou deploy (ou toca Dockerfile, workflows, Terraform, config de PaaS/Firebase/EAS), carregue também `devops-standards` e respeite a política de deploy: agente nunca faz deploy nem `apply`.
   **Design (obrigatório se a Issue cria ou altera UI** — tela, página, componente, estilo, tema, animação, em web ou mobile): siga o protocolo de `.claude/rules/10-ui-design.md`, nesta ordem: `design-references` (só peças públicas: 3–5 exemplos da galeria certa → `docs/design/references-<peça>.md`) → `ui-ux-pro-max` (busca de estilo/paleta/tipografia/UX para o domínio; `DESIGN.md`/tokens existentes têm prioridade) → `design-taste-frontend` (direção com `draw.mjs`, ou `draw.mjs --app` para telas de aplicativo) → `impeccable` (`impeccable context` uma vez por sessão; polish/audit antes do PR) → `frontend-design` e `emil-design-eng` durante a implementação → motion com `gsap-*` e `lenis` → `unslop-design` (`scripts/scan.py` + correções) → `web-design-guidelines` como auto-revisão final. Página pública: rode também `seo-audit` (`scripts/seo_check.py` no HTML renderizado) e `site-compliance` (`scripts/compliance_check.py`); documento legal faltando vira rascunho no PR + `needs-human`. Se um script não rodar no ambiente, aplique o conteúdo de `reference/` da skill manualmente e anote "modo degradado" — nunca pule a skill. As skills ficam em `.claude/skills/` deste repositório, então o protocolo vale igualmente em `exec:cloud` e `exec:orca`.
5. **Plano e orçamento (antes de codar):** escreva para si um plano de 3–8 linhas — tipo do PR (feat/fix/refactor/test/chore/docs), arquivos/camadas que vai tocar, patterns (com o problema que resolvem) e uma estimativa de linhas.
   - Orçamento pela label: `size:xs` ≤ 50, `size:s` ≤ 150, `size:m` ≤ 400 linhas (código + testes, sem gerados/lock/docs).
   - Se a estimativa passa do orçamento, ou o plano tem mais de um tipo (ex.: precisa de um refactor antes da feature), **não implemente**. Crie as sub-Issues seguindo o fatiamento de `small-prs.md` (template feature, critérios de aceite, `size:*`, `Depende de #N`, `Parte de #<numero>`, **sem** `agent:authorized`), comente o plano de divisão na Issue original, aplique `needs-human` e pare.
6. **Segurança ao escrever:** carregue a skill `owasp-security`. Se a Issue tem `security:sensitive`, liste em 3–5 linhas as ameaças relevantes e como o código vai tratá-las.
7. Implemente apenas o que os critérios de aceite pedem, com testes no mesmo PR. Sem mudanças de carona: nada de reformatar arquivos vizinhos, renomear fora do escopo ou atualizar dependências não pedidas — se notar algo, crie uma Issue. Nunca escreva segredos em código, logs, testes ou commits. Commits pequenos e com mensagem no padrão Conventional Commits. Ao terminar o código, delegue ao subagente `docs-writer` (número da Issue): ele atualiza API, modelo de dados, ADR, README/setup e runbooks no mesmo PR, quando o diff exigir.
8. **Meça durante o trabalho:** rode `python3 scripts/pr-size.py` a cada etapa concluída. Se for passar do orçamento, siga "Se o trabalho crescer no meio da implementação" em `small-prs.md` (abrir PR só com a fatia coerente e criar Issues de continuação, ou parar com `needs-human`).
9. **QA:** delegue ao subagente `qa-tester` passando o número da Issue. Se houver LACUNA, escreva o teste que falta. Se o veredito for FALHA, **não chute correções**: delegue ao subagente `debugger` (falha + número da Issue), aplique a correção mínima que ele propõe e rode o QA de novo (máximo 3 ciclos; depois aplique `needs-human` com o diagnóstico do debugger e pare).
10. Escreva `docs/handoff/<numero>.md`: estado atual, decisões tomadas (incluindo patterns e por quê), próximo passo, testes pendentes.
11. Faça o commit final. **Depois** do último commit, rode a varredura local de segurança no diff:
    - se existir `~/.claude/scripts/security-scan.sh`, rode-o;
    - senão, se `semgrep` estiver instalado: `semgrep scan --config p/default --config p/owasp-top-ten --severity ERROR --error --baseline-commit origin/main`;
    - senão, registre no PR que a varredura local não estava disponível e que o CI `security` cobre.
    Corrija achados críticos/altos, commite e rode de novo. Se não conseguir corrigir, aplique `needs-human` e NÃO abra o PR.
12. Rode `python3 scripts/pr-size.py` uma última vez. Acima de 800 linhas o CI reprova: não abra o PR, divida. Nunca aplique `size:exception` (só humanos).
13. Abra o PR com `gh pr create`: título em Conventional Commits, `Closes #<numero>`, template completo — **Escopo** ("Este PR faz uma coisa: …", tipo, saída do pr-size, Issues de continuação), **Como revisar** (ordem de leitura), **Design**, **Evidências**, **Segurança**.
14. Nunca faça merge. Pare após abrir o PR.
